##  목적

+ 조회 시 성능 저하가 발생할 수 있는 주요 기능을 선정하고, 쿼리 튜닝, 인덱스 설계, 테이블 구조 재검토 등을 통해 효율적인 DB 성능 개선 방안을 도출하는 것이 목적이다.

##  대상 기능 선정

### 1 잔액 조회

+ 단건 조회지만, 결제 및 잔액 사용·충전에서도 사용되는 기능으로 속도 보장이 필요하다.
+ 사용자 ID(`user_id`) 기반으로 잔액을 단건 조회한다.
+ `user_id`는 유니크하므로 단일 인덱스 생성으로 빠른 조회가 가능하다.

### 2 재고 조회

+ 결제 및 상품 구매 시 사용되는 기능으로 속도 보장이 필요하며, 상품이 많아질수록 성능 저하 위험이 있어 최적화가 필요하다.
+ 상품 ID(`product_id`) 기반의 단건 재고 조회이다.
+ `product_id`도 유니크한 값으로 단일 인덱스가 효과적이다.

### 3 사용자 쿠폰 조회

#### 조회 유형 1: 사용자 ID + 사용 가능 상태(`used_status`)
+ 사용 가능한 쿠폰 목록 조회 기능으로 사용자 수가 늘어날수록 성능 저하가 우려된다.
+ `user_id`: 카디널리티 높음
+ `used_status`: 카디널리티 낮음 → (`user_id`, `used_status`) 순서의 복합 인덱스가 유리하다.

#### 조회 유형 2: 사용자 ID + 쿠폰 ID

+ 단건 쿠폰 조회 시 사용되는 기능으로 성능 저하 우려는 낮으나, 복합 인덱스가 필요한지 검토가 필요하다.
+ 두 컬럼 모두 조건에 사용되므로 복합 인덱스가 효과적이다.

### 4 상품 조회

+ 판매 중인 상품 목록 전체 조회 기능이다.
+ 상품 수가 증가할수록 성능 저하가 우려된다.
+ "인덱스 + 페이징 처리(커서 기반)"를 통해 성능 최적화가 가능하다.

### 5 인기 상품 조회

+ 결제 이력을 기반으로 인기 상품을 조회하는 기능이다.
+ 실시간 조회는 쓰기 성능에 영향을 줄 수 있다.
+ 통계 테이블 + 배치 처리 전략, 인덱스 적용이 필요하다.
+ 비즈니스 요구사항이 바뀔 수 있는 우려가 있어, 이번에는 인덱스만 적용해서 성능을 최적화하기로 한다.

> 기타 기능은 대부분 PK 기반 단건 조회이며, 현재는 성능 이슈 우려가 낮다.

## 상세 분석 및 개선 내역

10만 건의 더미 데이터를 기반으로, `EXPLAIN ANALYZE` 명령어를 통해 인덱스 적용 전후의 성능을 분석하였다.

> `EXPLAIN ANALYZE`는 쿼리를 실제 실행하면서 각 연산의 비용, 실제 시간, 행 수를 분석할 수 있다.

###  잔액 조회

####  JPA
```java
balanceJpaRepository.findByUserId(userId);
```

#### 인덱스 적용 전
```sql
EXPLAIN ANALYZE SELECT * FROM balance WHERE user_id = 10000;
```
```text
-> Filter: (balance.user_id = 10000)  (cost=10089 rows=10016) (actual time=1.77..15.7 rows=1 loops=1)
    -> Table scan on balance  (cost=10089 rows=100163) (actual time=0.637..12.6 rows=100000 loops=1)
```

#### 인덱스 생성
```sql
CREATE INDEX idx_user_id ON balance(user_id);
```

#### 인덱스 적용 후
```text
-> Index lookup on balance using idx_user_id (user_id=10000)  (cost=0.35 rows=1) (actual time=0.0914..0.093 rows=1 loops=1)
```

15.7ms → 0.093ms (약 99.4% 개선)

### 사용자 쿠폰 조회


#### JPA (유형 2 : 사용자 ID + 쿠폰 ID)
```java
userCouponJpaRepository.findByUserIdAndCouponId(userId, couponId);
```

#### 인덱스 적용 전
```sql
EXPLAIN ANALYZE SELECT * FROM user_coupon WHERE user_id = 10 AND coupon_id = 11;
```
```text
-> Filter: ((user_coupon.coupon_id = 11) and (user_coupon.user_id = 10))  (cost=9827 rows=972) (actual time=0.114..18.5 rows=1 loops=1)
    -> Table scan on user_coupon  (cost=9827 rows=97227) (actual time=0.111..14.8 rows=100000 loops=1)
```

> `user_id` 선행 복합 인덱스(`idx_user_status`)가 이미 존재하면 옵티마이저가 해당 인덱스로 `user_id`를 좁힌 뒤 `coupon_id`를 필터링할 수 있다. (`user_id`, `coupon_id`) 접근 패턴 자체를 인덱스로 커버하기 위해 전용 복합 인덱스를 생성하고, `FORCE INDEX`로 그 효과를 검증하였다.

#### 인덱스 생성
```sql
CREATE INDEX idx_user_coupon ON user_coupon(user_id, coupon_id);
```

#### 인덱스 적용 후
```text
-> Index lookup on user_coupon using idx_user_coupon (user_id=10, coupon_id=11)  (cost=0.35 rows=1) (actual time=0.0271..0.0282 rows=1 loops=1)
```

18.5ms → 0.028ms (약 99.8% 개선)

### 상품 조회

#### JPA
```java
productJpaRepository.findBySellStatusIn(statuses);
```

#### 인덱스 적용 전
```sql
EXPLAIN ANALYZE SELECT * FROM product WHERE sell_status IN ('SELLING');
```
```text
-> Filter: (product.sell_status = 'SELLING')  (cost=10104 rows=9999) (actual time=0.0697..22.8 rows=90000 loops=1)
    -> Table scan on product  (cost=10104 rows=99993) (actual time=0.0688..14.3 rows=100000 loops=1)
```

#### 인덱스 생성
```sql
CREATE INDEX idx_sell_status ON product(sell_status);
```

#### 인덱스 적용 후
```text
-> Index lookup on product using idx_sell_status (sell_status='SELLING')  (cost=5312 rows=49996) (actual time=1.97..80.8 rows=90000 loops=1)
```

22.8ms → 80.8ms (약 254% 성능 저하)

+ `sell_status = 'SELLING'` 조건의 결과가 전체 상품의 약 90%를 차지한다.
+ 카디널리티가 낮은 컬럼이므로 전체 테이블 스캔이 더 빠르다.
+ 인덱스가 오히려 성능을 저하시킨다.

#### 일반 페이징 적용
```sql
SELECT * FROM product WHERE sell_status IN ('SELLING') LIMIT 0, 10;
```
```text
-> Limit: 10 row(s)  (cost=5312 rows=10) (actual time=0.0776..0.0789 rows=10 loops=1)
    -> Index lookup on product using idx_sell_status (sell_status='SELLING')  (cost=5312 rows=49996) (actual time=0.0769..0.0777 rows=10 loops=1)
```
+ `actual time=0.0776..0.0789` : 실제 쿼리 실행시간이 0.079ms 소요되었다.
+ `offset`이 깊어질수록 성능 저하가 발생할 수 있다.

#### 커서 기반 페이징 적용
```sql
SELECT * FROM product WHERE sell_status IN ('SELLING') AND product_id > 1050 LIMIT 0, 10;
```
```text
-> Limit: 10 row(s)  (cost=10016 rows=10) (actual time=0.0518..0.0645 rows=10 loops=1)
    -> Filter: ((product.sell_status = 'SELLING') and (product.product_id > 1050))  (cost=10016 rows=49996) (actual time=0.0511..0.0633 rows=10 loops=1)
        -> Index range scan on product using PRIMARY over (1050 < product_id)  (cost=10016 rows=49996) (actual time=0.0397..0.05 rows=11 loops=1)
```
+ `actual time=0.0518..0.0645` : 실제 쿼리 실행시간이 0.065ms 소요되었다.
+ `product_id`가 PK이므로 인덱스 스캔을 통해 빠른 조회가 가능하다.

#### 성능 비교
| 전략      | 쿼리 시간   | 특징                              |
|---------|---------|---------------------------------|
| 인덱스 미사용 | 22.8ms  | Full Table Scan이지만 오히려 효율적      |
| 인덱스 사용  | 80.8ms  | Row 수가 너무 많아 비효율적               |
| 일반 페이징  | 0.079ms | 작은 OFFSET에선 빠르나, 페이지가 깊어질수록 느려짐 |
| 커서 페이징  | 0.065ms | 인덱스 스캔을 통해 빠른 조회 성능             |

### 인기 상품 조회

#### JPA (결제 정보 조회)
```java
paymentJpaRepository.findByPaymentStatusInAndPaidAtBetween(statuses, startDateTime, endDateTime);
```

#### 인덱스 적용 전
```sql
EXPLAIN ANALYZE
SELECT * FROM payment
WHERE payment_status IN ('COMPLETED')
AND paid_at BETWEEN '2024-01-01' AND '2024-01-31';
```
```text
-> Filter: ((payment.payment_status = 'COMPLETED') and (payment.paid_at between '2024-01-01' and '2024-01-31'))  (cost=10108 rows=11097) (actual time=0.404..42.1 rows=8493 loops=1)
    -> Table scan on payment  (cost=10108 rows=99880) (actual time=0.356..19 rows=100000 loops=1)
```

#### 인덱스 생성

+ `payment_status`: 카디널리티가 낮을 가능성이 높지만, IN 조건이 먼저 나오므로 선행 컬럼으로 지정한다.
+ `paid_at`: 범위 조건(BETWEEN)이기 때문에, 복합 인덱스의 두 번째 컬럼으로 배치한다.

```sql
CREATE INDEX idx_payment_status_paid_at ON payment(payment_status, paid_at);
```

#### 인덱스 적용 후
```text
-> Index range scan on payment using idx_payment_status_paid_at over (payment_status = 'COMPLETED' AND '2024-01-01 00:00:00' <= paid_at <= '2024-01-31 00:00:00'), with index condition: ((payment.payment_status = 'COMPLETED') and (payment.paid_at between '2024-01-01' and '2024-01-31'))  (cost=7234 rows=16076) (actual time=2.6..25.4 rows=8493 loops=1)
```

42.1ms → 25.4ms (약 39.7% 개선)

> 조회 범위가 전체 데이터의 약 25% 이상이 되면 옵티마이저가 풀 스캔을 선택해 인덱스 효과가 사라진다. 범위 조건의 선택도(selectivity)가 충분히 높을 때 복합 인덱스가 유효함을 확인하였다.

18.7ms → 6.8ms (약 63.6% 개선)

## 결론 및 향후 계획

### 결론 요약
+ 총 5개 주요 기능에 대한 인덱스 적용을 통해 최대 99.8%의 성능 개선 효과를 확인하였다.
+ 특히 잔액 조회, 사용자 쿠폰 조회 등 핵심 트래픽 구간에서 대폭 개선되었다.
+ 반면, 카디널리티가 낮은 컬럼에 대한 인덱스(상품 `sell_status`)는 오히려 성능 저하를 유발하여, 커서 기반 페이징으로 대체하였다.
+ 범위 조건(결제 `paid_at`)은 조회 범위의 선택도가 충분히 높을 때에만 인덱스가 유효함을 확인하였다.

### 향후 계획

#### 인덱스 한계
+ 인덱스로 해결이 어려운 경우, Sync Schedule Strategy, Materialized View, Sharding 등 구조적 대안을 검토한다.

#### 기술적 확장 고려
+ Redis, Elasticsearch 등 서브 시스템 도입을 통한 분산 처리 전략을 수립한다.

#### CQRS 기반의 인프라 디자인
+ 조회(Read)는 리플리케이션 DB(슬레이브)로 분리하고, 쓰기(Write)는 마스터 DB에서 처리하는 구조로 전환하여 읽기 부하 분산 및 서비스 확장성을 확보한다.
