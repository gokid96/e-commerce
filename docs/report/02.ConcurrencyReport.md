# 동시성 이슈 분석 및 해결 보고서

## 배경

다중 요청 환경에서는 여러 트랜잭션이 같은 데이터를 동시에 읽고 쓸 수 있다. 이때 각 트랜잭션이 다른 트랜잭션의 갱신을 보지 못한 채 이전 값을 기준으로 계산하면, 한쪽의 변경이 다른 쪽에 덮여 사라지는 갱신 분실(lost update)이 발생한다. 본 보고서는 잔액, 쿠폰, 재고 세 기능에서 발생 가능한 동시성 문제를 분석하고, 데이터베이스 락으로 해결한 과정과 검증 결과를 정리한다.

## 문제 분석

### 1. 잔액 충전 및 차감

동일 사용자의 잔액에 충전·사용 요청이 동시에 들어오면, 두 트랜잭션이 같은 잔액을 읽고 각각 계산해 저장한다. 두 요청 모두 처리된 것으로 보이지만 실제 잔액에는 한 번만 반영되어, 충전 금액이 사라지거나 사용 한도를 넘겨 차감되는 등 정합성이 깨진다.

### 2. 선착순 쿠폰 발급

한정 수량 쿠폰에 다수 요청이 몰리면, 여러 트랜잭션이 같은 잔여 수량을 읽고 각각 차감한다. 그 결과 수량이 음수가 되거나 발급 한도를 넘는 초과 발급이 발생한다. 또한 한 사용자가 같은 쿠폰을 동시에 여러 번 요청하면 중복 발급될 수 있다.

### 3. 재고 차감

인기 상품 주문이 몰리면 같은 재고 행을 동시에 읽고 각각 차감한다. 재고가 음수가 되어 실제 보유량보다 많이 판매되는 과판매가 발생한다.

## 해결 방안: 데이터베이스 락

### 락이란

락은 특정 데이터에 대한 동시 접근을 제어해, 한 트랜잭션이 작업하는 동안 다른 트랜잭션의 접근을 제한하는 메커니즘이다. 접근 방식에 따라 낙관적 락과 비관적 락으로 나뉜다.

### 낙관적 락 (Optimistic Lock)

충돌이 드물게 발생한다고 가정한다. 데이터에 버전 컬럼을 두고, 갱신 시점에 읽었던 버전과 현재 버전이 다르면 충돌로 판단해 실패시킨다. 락을 미리 잡지 않으므로 대기 비용이 없고, 충돌이 일어난 경우에만 실패(또는 재시도)한다.

### 비관적 락 (Pessimistic Lock)

충돌이 자주 발생한다고 가정한다. 데이터를 읽는 시점에 데이터베이스 락(SELECT ... FOR UPDATE)을 잡아, 트랜잭션이 끝날 때까지 다른 트랜잭션의 접근을 막는다. 동시 요청을 직렬화하므로 충돌 자체를 방지하지만, 대기와 처리량 저하가 따른다.

### 락 전략 선택 기준

- 충돌 빈도가 낮으면 낙관적 락을 택한다. 대부분 정상 처리되고 불필요한 락 비용을 피한다.
- 충돌 빈도가 높으면 비관적 락을 택한다. 잦은 실패와 재시도 폭주를 피하고, 직렬화로 정합성을 보장한다.

### JPA 락 설정

- 낙관적 락: 엔티티에 `@Version` 필드를 둔다. 갱신 시 버전이 일치하지 않으면 예외가 발생한다.
- 비관적 락: 조회 메서드에 `@Lock(LockModeType.PESSIMISTIC_WRITE)`를 둔다. 활성 트랜잭션 안에서만 동작하므로, 락 조회는 서비스의 `@Transactional` 메서드 안에서 호출한다.

## 동시성 제어 방식 선정

### 1. 잔액 — 낙관적 락

개인 잔액은 동시에 변경되는 경우가 흔하지 않다. 동시 요청은 비정상에 가까우며, 이 경우 하나만 성공하고 나머지는 실패시키는 것이 허용 가능한 결과다. 따라서 `@Version` 기반 낙관적 락으로 충돌을 감지하고, 충돌한 요청은 실패 처리한다.

- 적용: `Balance`에 `@Version`, `BalanceService.chargeBalance` / `useBalance`에 `@Transactional`.

### 2. 쿠폰 — 비관적 락 + 유니크 제약

선착순 발급은 한정 수량에 다수가 동시에 몰리는, 충돌 빈도가 매우 높은 경우다. 비관적 락으로 수량 차감을 직렬화해 초과 발급을 막는다. 또한 `(user_id, coupon_id)` 유니크 제약과 발급 전 검증으로 한 사용자의 중복 발급을 막는다.

- 적용: `CouponJpaRepository.findWithLockById`에 `@Lock`, `CouponService.issueCoupon`에 `@Transactional`, `UserCoupon`에 `uk_user_coupon` 유니크 제약과 중복 발급 검증.

### 3. 재고 — 비관적 락

인기 상품은 동일 재고 행에 주문이 몰려 충돌 빈도가 높다. 비관적 락으로 차감을 직렬화해 과판매를 막는다.

- 적용: `StockJpaRepository.findWithLockByProductId`에 `@Lock`, `StockService.deductStock`에서 락 조회 사용.

## 테스트를 통한 검증

공통적으로 `ConcurrencyTestSupport`(ExecutorService + CompletableFuture)로 동시 요청을 발생시키고, 성공/실패 수와 최종 데이터를 검증했다. 검증 조회는 락을 잡지 않는 finder를 사용한다.

### 1. 잔액 (낙관적 락)

- 시나리오: 잔액 1,000원에 동시에 충전 1,000원 2건.
- 기대 결과: 1건 성공, 1건 실패, 최종 2,000원.
- AS-IS (락 미적용): 두 요청이 같은 1,000원을 읽고 각각 2,000원을 저장한다. 두 요청 모두 성공한 것처럼 보이지만 한 건의 충전이 분실된다.
- TO-BE (락 적용): 한 건만 성공하고 나머지는 충돌로 실패한다. 최종 2,000원이며 실패한 요청은 명시적으로 거부된다.

사용 시나리오(잔액 1,000원에 동시 사용 500원 2건)와 충전·사용 혼합 시나리오에서도 동일하게 한 건만 성공함을 확인했다.

### 2. 쿠폰 (비관적 락)

- 시나리오 A: 수량 5, 서로 다른 사용자 2명이 동시 발급 → 2건 성공, 남은 수량 3.
- 시나리오 B: 수량 1, 2명이 동시 발급 → 1건 성공, 1건 실패, 남은 수량 0.
- 중복 발급: 같은 사용자가 같은 쿠폰을 다시 발급 시도 → "이미 발급된 쿠폰입니다." 예외.
- AS-IS (락 미적용): 수량 1에 2건이 동시에 잔여 1을 읽고 각각 발급해 초과 발급(수량 음수)이 발생한다.
- TO-BE (락 적용): 비관적 락으로 차감이 직렬화되어 1건만 발급되고 남은 수량은 0이 된다.

### 3. 재고 (비관적 락)

- 시나리오 A: 재고 10, 동시에 1씩 차감 2건 → 2건 성공, 남은 재고 8.
- 시나리오 B: 재고 1, 동시 2건 → 1건 성공, 1건 실패, 남은 재고 0.
- AS-IS (락 미적용): 재고 1에 2건이 동시에 1을 읽고 각각 차감해 과판매(재고 음수)가 발생한다.
- TO-BE (락 적용): 차감이 직렬화되어 1건만 성공하고 남은 재고는 0이 된다.

## 한계

### 비즈니스 측면

낙관적 락에서 충돌한 요청은 실패로 끝난다. 현재는 실패 처리만 하며 별도의 재시도 정책은 두지 않았다. 사용자 경험상 자동 재시도가 필요하다면 정책을 추가해야 한다.

### 순서 보장

어느 요청이 먼저 성공할지는 보장되지 않는다. 선착순에서 "먼저 도착한 요청"과 실제 성공 순서가 항상 일치하지는 않는다.

### 성능 측면

비관적 락은 동시 요청을 직렬화하므로 처리량이 떨어지고, 락 대기와 데드락 가능성이 있다. 트래픽이 큰 구간에서는 병목이 될 수 있다.

### 분산 환경

데이터베이스 락은 단일 데이터베이스를 기준으로 한다. 다중 인스턴스·분산 환경에서는 한계가 있어, 분산 락이 별도로 필요하다.

## 결론

잔액은 충돌이 드물어 낙관적 락을, 쿠폰과 재고는 충돌이 잦아 비관적 락을 적용했다. 쿠폰은 유니크 제약과 발급 전 검증으로 중복 발급까지 막았다. 동시성 테스트를 통해 락 적용 후 초과 발급, 과판매, 갱신 분실이 사라지는 것을 확인했다.
