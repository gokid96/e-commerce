# MSA 부하 테스트 보고서

> 모놀리식 구조에서의 부하 테스트는 [07. 부하 테스트 보고서](07.LoadTestReport.md)에서 다룬다.
> 서비스를 6개로 분리한 뒤 동일 시나리오를 재측정해보자

## 배경

STEP09의 부하 테스트는 단일 애플리케이션 컨테이너(2 vCPU / 4 GB)를 대상으로 수행하였다.  
도메인 단위로 서비스를 분리하면서 두 가지 조건이 달라졌다.

- **서비스 간 호출이 인프로세스 메서드 호출에서 네트워크 호출로 전환되었다.** 주문 한 건을 처리하기 위해 Feign 5회와 Kafka 왕복 2회를 경유한다.
- **자원 배분 단위가 애플리케이션에서 서비스로 변경되었다.** 단일 컨테이너에 2 vCPU를 할당하던 구성에서, 6개 서비스에 각각 1 vCPU를 할당하는 구성으로 변경하였다.

본 측정의 목적은 두 가지이다.

1. **서비스 단위로 자원을 제한한 조건에서** 병목 지점을 재식별하고 TPS 기준의 Pod 수를 산정한다.
2. **분산 구조로 전환함에 따른 비용을 정량적으로 확인한다.** 처리량과 꼬리 지연의 변화를 각각 측정한다.

## 대상

부하 테스트의 대상은 시스템의 핵심 비즈니스 기능을 기준으로 선정하였다.  
이번 테스트에서는 주문/결제 시나리오와 선착순 쿠폰 발급 시나리오를 중심으로 진행한다.

### 주문/결제

주문/결제는 사용자 경험과 직접적으로 연결된 핵심 서비스 기능으로,  
실제 사용 흐름을 기반으로 시나리오를 구성하여 부하 테스트를 수행하였다.

테스트 시나리오는 다음 단계로 구성된다.

1. 인기상품 조회
2. 잔액 충전
3. 잔액 조회
4. 주문 생성
5. 주문 완료 상태 확인

실제 사용자 전체가 상품을 조회한 후 주문까지 진행하지는 않기 때문에,  
현실적인 사용자을 반영하여 다음 가정을 두고 테스트를 구성하였다.

- 전체 사용자 중 20% 사용자만 잔액 충전
- 충전 사용자 중 10% 사용자만 주문

5단계를 반드시 포함시켰다. 주문/결제는 `ORDER_CREATED` → 결제 → 잔액 차감 → `PAYMENT_PAID` → 주문 완료로 이어지는 이벤트 기반 사가로 처리되므로,  
주문 생성 API가 200을 반환하는 것만으로는 거래가 완결되었다고 볼 수 없다.  
**주문 생성 후 일정 시간이 지난 뒤 주문 상태가 `COMPLETED`가 되었는지 확인해야 부하 상황에서 사가가 완주하는지 알 수 있다.**

### 선착순 쿠폰 발급

선착순 쿠폰 발급 기능은 시스템 내에서 가장 높은 단일 시점 트래픽이 집중되는 기능이다.  
이 기능의 안정성을 검증하기 위해, 고부하 상황을 집중적으로 발생시키는 Peak Test로 시나리오를 구성하였다.

특정 시점에 다수의 사용자가 동시에 쿠폰을 요청하는 상황을 재현하여,  
트래픽 집중 시의 응답 시간, 처리율, 에러 발생 여부 등을 중점적으로 검증한다.

## 테스트 환경 구축

테스트 환경은 로컬 PC의 도커 컨테이너를 활용하여 구성하였다.

### Spring 테스트 환경

MSA로 분리된 6개 서비스를 각각 컨테이너로 기동한다.  
서비스별 리소스를 제한하여 측정 조건을 고정하고, TPS 기준의 Pod 수 산정이 의미를 갖도록 하였다.  
다음은 `service-compose.yml` 일부이다.

```yaml
services:
  product-api:
    build:
      context: service/product
      dockerfile: Dockerfile
    ports:
      - "8084:8084"
    environment:
      - SPRING_PROFILES_ACTIVE=dev
      - TZ=Asia/Seoul
    deploy:
      resources:
        limits:
          cpus: '1.0'
          memory: 2G
    networks:
      - ecommerce
```

**서비스당 CPU 1 vCPU, 메모리 2 GB로 제한하였다.** MySQL,Redis,Kafka 등 인프라 컨테이너에는 제한을 두지 않았다.  
인프라는 `infra-compose.yml`로 분리하여, 인프라만 띄운 상태에서 애플리케이션을 로컬에서 실행하는 것도 가능하도록 구성하였다.

#### 측정 대상 구조

주문 한 건이 완결되기까지 거치는 경로는 다음과 같다. 모든 서비스 간 통신이 네트워크를 경유한다.

```
[주문 생성]  order ──HTTP──> product  (상품 조회)
             order ──HTTP──> coupon   (쿠폰 검증)
             order ──HTTP──> product  (재고 차감)
             order ──Kafka─> ORDER_CREATED

[결제]       payment <─Kafka─ ORDER_CREATED
             payment ─HTTP──> balance  (잔액 차감)
             payment ─HTTP──> coupon   (쿠폰 사용)
             payment ─Kafka─> PAYMENT_PAID

[주문 완료]  order <──Kafka── PAYMENT_PAID
             order ──Kafka─> ORDER_COMPLETED
```

**주문 1건당 동기 HTTP 호출 5회, Kafka 왕복 2회**가 발생하며, 각 구간의 직렬화/역직렬화와 네트워크 지연이 응답 시간에 누적된다.  
구조적 비용이 측정 결과의 꼬리 지연에 어떻게 반영되는지를 중점적으로 확인한다.

```groovy
configure(subprojects.findAll { it.path.startsWith(':service:') }) {
```

```yaml
global:

scrape_configs:
```


### K6 테스트 환경

부하 테스트 도구로는 K6를 사용하였으며, InfluxDB 및 Grafana와 연동하여 테스트 결과를 시각화하였다.  
다음은 InfluxDB와 Grafana를 위한 `infra-compose.yml` 일부이다.

```yaml
services:
  influxdb:
    image: influxdb:1.8
    ports:
      - "8086:8086"
    environment:
      INFLUXDB_DB: k6
    networks:
      - ecommerce

  grafana:
    image: grafana/grafana:latest
    ports:
      - "3000:3000"
    environment:
      GF_AUTH_ANONYMOUS_ENABLED: "true"
      GF_AUTH_ANONYMOUS_ORG_ROLE: Admin
    volumes:
      - ./grafana/provisioning:/etc/grafana/provisioning:ro
      - ./grafana/dashboards:/etc/grafana/dashboards:ro
    networks:
      - ecommerce
```

데이터소스와 대시보드는 프로비저닝으로 자동 등록하여, 매번 UI에서 설정하지 않도록 하였다.

- InfluxDB(k6 지표) + Prometheus(Actuator 지표) 데이터소스
- k6 결과 대시보드 [2587](https://grafana.com/grafana/dashboards/2587-k6-load-testing-results/)
- JVM 지표 대시보드 [4701](https://grafana.com/grafana/dashboards/4701-jvm-micrometer/)

K6 실행 시 `--out influxdb=http://localhost:8086/k6` 옵션으로 측정 지표를 InfluxDB로 전송하고, Grafana 대시보드에서 API별 응답 시간을 관찰하였다.

## 테스트 설계 및 목적

### 주문/결제

#### 테스트 시나리오

주문/결제 기능은 단기간 폭증보다는 일정 수준의 트래픽이 지속적으로 유지되는 특성이 있으므로,  
Load Test 방식으로 최대 300(VU)까지 점진적으로 증가시키는 테스트를 설계하였다.

1. 10초 동안 100 VU 까지 증가
2. 10초 동안 200 VU 까지 증가
3. 10초 동안 300 VU 까지 증가
4. 30초 동안 300 VU 유지
5. 10초 동안 100 VU 까지 감소
6. 10초 동안 50 VU 까지 감소
7. 10초 동안 0 VU 까지 감소

#### 목표 TPS

목표 TPS는 **동시 사용자 100명이 각 기능을 얼마나 자주 호출하는지**를 기준으로 산정하였다.

| 기능      | 사용자 기준 | 처리 빈도    | 목표 TPS  |
|---------|--------|----------|---------|
| 인기상품 조회 | 100명   | 1초에 1건   | 100 TPS |
| 잔액 충전   | 100명   | 10초에 1건  | 10 TPS  |
| 주문 생성   | 100명   | 100초에 1건 | 1 TPS   |

#### 테스트 데이터

##### 랭킹 데이터 생성

인기상품 조회 시 필요한 랭킹 데이터를 Redis에 사전 적재하였다. 기준일 포함 최근 4일치 키에 상품 50건을 넣는다.

```redis
ZADD rank:sell:{yyyyMMdd} {score : 판매량} {productId : 상품 ID}
```

##### 상품·재고·사용자·잔액 데이터 생성

`sql/fixture.sql`로 적재한다. 재귀 CTE와 `INSERT ... SELECT`를 사용해 1만 건 단위 적재를 즉시 완료한다.

```sql
-- 상품 1만 건
INSERT INTO product (name, price, sell_status)
WITH RECURSIVE seq AS (
    SELECT 1 AS n
    UNION ALL
    SELECT n + 1 FROM seq WHERE n < 10000
)
SELECT CONCAT('상품명', n), 1000, 'SELLING' FROM seq;

-- 재고 1만 건 (상품과 1:1)
INSERT INTO stock (product_id, quantity)
SELECT product_id, 1000 FROM product;

-- 잔액 1만 건 (낙관적 락 version 포함)
INSERT INTO balance (user_id, amount, version)
SELECT user_id, 1000000, 0 FROM `user`;
```


#### 테스트 스크립트

##### SLA 설정

- **HTTP 요청의 P99 응답 시간**은 **1초 이하**를 목표로 한다.
- **HTTP 요청 실패율**은 **1% 미만**으로 제한한다.

##### 시나리오 구성

1. 인기상품 조회 : 인기상품 목록을 조회한 후, **응답받은 상품 중 하나를 랜덤으로 선택**한다.
2. 잔액 충전 : **20% 확률로 잔액을 충전**하고, 이어서 **잔액을 조회**한다.
3. 주문 생성 : **10% 확률로 선택된 상품을 주문**한다.
4. 주문 상태 확인 : 주문/결제는 이벤트 기반 사가로 처리되므로, **2초 지연 후 상태 조회 API를 호출**하여 주문 상태가 `"COMPLETED"`로 변경되었는지 확인한다.

```javascript
import http from 'k6/http';
import { sleep, check, group } from "k6";
import { randomIntBetween } from 'https://jslib.k6.io/k6-utils/1.2.0/index.js';

export const options = {
    stages: [
        { duration: '10s', target: 100 },
        { duration: '10s', target: 200 },
        { duration: '10s', target: 300 },
        { duration: '30s', target: 300 },
        { duration: '10s', target: 100 },
        { duration: '10s', target: 50 },
        { duration: '10s', target: 0 }
    ],
    thresholds: {
        http_req_duration: ['p(99)<1000'],
        http_req_failed: ['rate<0.01']
    }
};

const PRODUCT_URL = 'http://127.0.0.1:8084/api/v1';
const BALANCE_URL = 'http://127.0.0.1:8082/api/v1';
const ORDER_URL = 'http://127.0.0.1:8085/api/v1';

const ORDER_CHECK_INTERVAL = 2;

export default function main() {
    const userId = randomIntBetween(1, 10000);

    let orderId = null;
    let shouldOrder = false;
    let shouldChargeBalance = false;
    let selectedProduct = null;

    group('주문/결제 시나리오', () => {
        const popularProductsResponse = http.get(`${PRODUCT_URL}/products/ranks`, {
            tags: { name: '인기상품조회' }
        });
        check(popularProductsResponse, {
            '인기상품 조회 성공': (r) => r.status === 200,
            '인기상품 데이터 확인': (r) => {
                if (r.status !== 200) return false;
                const body = JSON.parse(r.body);
                return body.data && Array.isArray(body.data.products) && body.data.products.length > 0;
            }
        });

        if (popularProductsResponse.status === 200) {
            const body = JSON.parse(popularProductsResponse.body);
            if (body.data && Array.isArray(body.data.products) && body.data.products.length > 0) {
                const products = body.data.products;
                selectedProduct = products[Math.floor(Math.random() * products.length)];
                shouldChargeBalance = Math.random() < 0.2;
            }
        }

        if (shouldChargeBalance) {
            const payload = JSON.stringify({ amount: 10000 });
            const params = {
                headers: { 'Content-Type': 'application/json' },
                tags: { name: '잔액충전' }
            };
            const chargeResponse = http.post(`${BALANCE_URL}/users/${userId}/balance/charge`, payload, params);
            check(chargeResponse, {
                '잔액 충전 성공': (r) => r.status === 200 && JSON.parse(r.body).code === 200
            });

            const balanceResponse = http.get(`${BALANCE_URL}/users/${userId}/balance`, {
                tags: { name: '잔액조회' }
            });
            check(balanceResponse, {
                '잔액 조회 성공': (r) => r.status === 200 && JSON.parse(r.body).data.amount !== undefined
            });

            shouldOrder = Math.random() < 0.1;
        }

        if (shouldOrder && selectedProduct) {
            const orderPayload = JSON.stringify({
                userId: userId,
                products: [
                    { productId: selectedProduct.id, quantity: 1 }
                ]
            });
            const orderParams = {
                headers: { 'Content-Type': 'application/json' },
                tags: { name: '주문생성' }
            };
            const orderResponse = http.post(`${ORDER_URL}/orders`, orderPayload, orderParams);
            check(orderResponse, {
                '주문 생성 성공': (r) => r.status === 200,
                '주문 ID 확인': (r) => {
                    if (r.status !== 200) return false;
                    const body = JSON.parse(r.body);
                    if (body.data && body.data.orderId) {
                        orderId = body.data.orderId;
                        return true;
                    }
                    return false;
                }
            });

            // 주문/결제는 이벤트 기반 사가로 처리되므로, 일정 시간 대기 후 최종 상태를 확인한다.
            if (orderId) {
                sleep(ORDER_CHECK_INTERVAL);

                const orderStatusResponse = http.get(`${ORDER_URL}/orders/${orderId}`, {
                    tags: { name: '주문상태확인' }
                });
                check(orderStatusResponse, {
                    '주문 상태 조회 성공': (r) => r.status === 200,
                    '주문 완료 확인': (r) => {
                        if (r.status !== 200) return false;
                        const body = JSON.parse(r.body);
                        return body.data && body.data.status === 'COMPLETED';
                    }
                });
            }
        } else {
            sleep(1);
        }
    });

    sleep(1);
}
```

### 선착순 쿠폰 발급

#### 테스트 시나리오

선착순 쿠폰 발급은 이벤트성 트래픽이 단시간에 집중되는 비즈니스로,  
급격한 부하가 집중되는 Peak Test 방식으로 최대 1000 VU까지 테스트를 진행한다.

1. 10초 동안 10 VU 까지 증가
2. 10초 동안 10 VU 유지
3. 10초 동안 700 VU 까지 증가
4. 10초 동안 10 VU 까지 감소
5. 10초 동안 10 VU 유지
6. 10초 동안 1000 VU 까지 증가
7. 10초 동안 10 VU 까지 감소
8. 10초 동안 0 VU 까지 감소

#### 목표 TPS

주문/결제와 동일한 기준(동시 사용자 100명 + 처리 빈도)으로 산정하였다.

| 기능    | 사용자 기준 | 처리 빈도  | 목표 TPS  |
|-------|--------|--------|---------|
| 쿠폰 발급 | 100명   | 1초에 1건 | 100 TPS |

#### 테스트 데이터

발급 가능 상태의 쿠폰 1건을 생성하였다.

```sql
INSERT INTO coupon (name, quantity, discount_rate, expired_at, status)
VALUES ('쿠폰명1', 100000, 0.3, DATE_ADD(NOW(), INTERVAL 7 DAY), 'PUBLISHABLE');
```

쿠폰 발급 가능 여부를 확인하는 플래그를 Redis에 적재하였다.

```redis
SET coupon_available:1 true
```

#### 테스트 스크립트

##### SLA 설정

### 선착순 쿠폰 발급

선착순 쿠폰 발급 Peak Test 결과, P99 기준 16.69초의 응답 지연과 35.3 TPS의 낮은 처리량이 확인되었다.  
해결하기 위해 개선 작업을 수행하였다.

- 쿠폰 발급 요청 흐름에 **Redis 선차단 + Kafka 비동기 처리** 도입
  (요청은 발급 가능 여부만 Redis로 확인하고 즉시 이벤트를 발행하며, 실제 수량 차감 및 발급은 컨슈머가 처리)
- 컨슈머 실패 시 **재시도 3회 후 DLT 격리** (`common:message`의 공통 에러 핸들러)

특히 발급 요청이 이벤트 발행만 수행하고 즉시 응답하게 되면서, **동일 쿠폰에 대한 행 경합이 응답 경로에서 제거되었다.**

원인은 발급 요청 경로에 여전히 남아 있는 두 가지 동기 작업으로 예상된다.

1. Redis 발급 가능 여부 조회
2. 아웃박스 레코드 저장: `@TransactionalEventListener(BEFORE_COMMIT)`으로 비즈니스 트랜잭션에 포함되므로, 요청 응답 전에 DB 쓰기가 완료되어야 한다

Kafka로 비동기 전환했지만 **아웃박스 저장이라는 동기 DB 쓰기가 응답 경로에 남아 있다.**  
이는 트랜잭셔널 아웃박스 패턴이 원자성을 보장하는 대가이며, 이벤트 유실 방지와 응답 지연 사이의 트레이드오프다.

개선 방향은 다음 두 가지이다.

- **스케일 아웃**: 서비스당 1 vCPU 기준 98 TPS이므로, 목표 TPS와 P99를 동시에 만족시키려면 coupon 서비스 Pod 2개 이상이 필요하다.
- **응답 경로 단축**: 아웃박스 저장을 요청 트랜잭션에서 분리하는 방식을 검토할 수 있으나, 이벤트 유실 위험이 생기므로 재발행 스케줄러 활성화가 선행되어야 한다.

- **쿠폰 발급**: Redis 선차단 + Kafka 비동기 발급 → P99 16.69s → 2.11s, 요청 처리량 +166.1%

### 모놀리식 대비 분산 전환 비용

[07. 부하 테스트 보고서](07.LoadTestReport.md)의 모놀리식 측정과 개선 후(TO-BE) 수치를 비교하면 다음과 같다.

| 지표          | 모놀리식 (STEP09) | MSA (STEP10) | 변화  |
|-------------|--------------:|-------------:|-----|
| 처리량         | 130.00/s      | 124.82/s     | 유지  |
| 반복(시나리오 완주) | 90.47/s       | 86.51/s      | 유지  |
| 평균 응답시간     | 5.68 ms       | 62.78 ms     | 11배 |
| P99         | 27.26 ms      | 471.39 ms    | 17배 |
| P99.9       | 40.05 ms      | 2.00 s       | 50배 |

> 두 측정의 조건이 다르다. 모놀리식 측정은 단일 컨테이너에 2 vCPU / 4 GB를 할당했고,
> MSA 측정은 6개 서비스에 각각 1 vCPU / 2 GB를 할당하였다. 총량은 늘었지만 서비스별로는 절반이다.
> 따라서 이 표는 아키텍처 비교가 아니라
> **자원을 쪼개고 서비스를 분리했을 때 무엇을 잃고 무엇을 지켰는가** 를 보여주는 값이다.

**처리량은 유지되었다.** 서비스를 6개로 분리하고 서비스당 CPU를 절반으로 축소하였음에도, 초당 처리량(125 TPS)과  
시나리오 완주율(87/s)은 모놀리식 수준을 유지하였다. 이는 병목이 특정 서비스에 국한되어 전체로 전파되지 않았음을 의미한다.

**반면 꼬리 지연은 악화되었다.** P99는 약 17배, P99.9는 약 50배 증가하였다.  
주된 원인은 주문 1건당 발생하는 5회의 동기 HTTP 호출이다. 각 구간의 지연은 평상시 수 ms 수준이지만,  
특정 서비스가 GC 또는 커넥션 대기로 일시적으로 지연되면 해당 지연이 호출 체인을 따라 누적된다.  
이는 단일 프로세스 구조에서는 존재하지 않던 실패 유형이다.

AS-IS 측정의 **주문 생성 P50 10.03초**가 이를 명확히 보여준다. product 서비스에 병목이 발생하자,  
해당 서비스를 세 번 호출하는 주문 생성의 응답 시간이 10초대로 증가하였다.  
모놀리식 구조에서는 동일한 부하에서도 인프로세스 호출이므로 이러한 지연 증폭이 발생하지 않는다.

따라서 분산 구조에서는 다음과 같은 방어 체계가 필수적이다.

- **Feign 타임아웃 및 서킷 브레이커**: 특정 서비스의 지연이 호출자의 스레드와 DB 커넥션을 점유하지 않도록 차단
- **호출 체인 축소**: 트랜잭션 내부에서 원격 호출을 수행하는 구간(주문 생성의 재고 차감, 결제의 잔액 차감)을 트랜잭션 외부로 분리

### 측정 지표 선정에 대한 시사점

이번 테스트에서 확인한 가장 중요한 사항은, **응답 시간 지표만으로는 이벤트 기반 시스템의 실패를 식별할 수 없다**는 점이다.

AS-IS 측정에서 주문 생성 API는 정상 응답(200)을 반환하였으나, 해당 주문 중 84%는 2초 이내에 `COMPLETED`에 도달하지 못하였다.  
API 응답 시간 지표만 관찰하였다면 "지연은 있으나 정상 동작한다"고 판단하였을 것이다.  
사가의 최종 상태를 확인하는 단계를 시나리오에 포함하였기 때문에, **부하 상황에서 거래가 완결되지 않는다**는 보다 중대한 문제를 식별할 수 있었다.

따라서 이벤트 기반 아키텍처의 부하 테스트에서는 요청-응답 지표와 별개로,  
**최종 일관성 도달 여부와 도달 시간**을 반드시 측정 대상에 포함해야 한다.

### 향후 과제

- **쿠폰 발급 P99 개선**: 아웃박스 저장을 비즈니스 트랜잭션에서 분리하거나, Pod 스케일 아웃으로 SLA 충족
- **서킷 브레이커 적용**: 서비스 간 동기 호출(Feign)에 타임아웃과 서킷 브레이커를 적용해 장애 전파 차단
- **모니터링 및 알림**: Prometheus 지표 기반 임계치 알림 체계 구축
- **스키마 관리 전환**: `ddl-auto: create`를 마이그레이션 도구로 대체해 재기동 시 데이터가 유지되도록 개선
