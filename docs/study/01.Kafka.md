# Kafka 기초 및 핵심 개념

## Kafka란

Kafka는 대용량 데이터를 높은 처리량으로 발행·저장·소비할 수 있는 **분산 이벤트 스트리밍 플랫폼**이다. 메시지를 메모리가 아닌 **디스크에 영속**시키고 여러 브로커에 **복제**하기 때문에, 단순한 메시지 전달을 넘어 이벤트의 **보관·재처리·순서 보장**까지 지원한다.

## 왜 도입하는가

본 프로젝트는 지금까지 도메인 간 협력을 **Spring ApplicationEvent**(인메모리, 단일 JVM) 기반의 이벤트로 구현해 왔다. 이 방식은 하나의 애플리케이션 안에서는 잘 동작하지만 다음 한계가 있다.

- 단일 인스턴스 내에서만 이벤트가 전파된다. → 서비스를 물리적으로 분리(MSA)하면 이벤트가 프로세스 경계를 넘지 못한다.
- 이벤트가 메모리에만 존재한다. → 애플리케이션이 죽으면 처리 중이던 이벤트가 **유실**되고 재처리할 수 없다.
- 순서 보장·중복 제거·재시도 같은 전달 신뢰성 기능이 없다.

Kafka는 이 문제들을 네트워크 메시지 브로커로 해결하며, 다음 이점을 제공한다.

- **높은 처리량**: 파티션 기반 병렬 처리로 초당 대량의 이벤트를 처리한다.
- **내구성**: 메시지를 디스크에 저장하고 복제하여 데이터 손실을 방지한다.
- **순서 보장**: 같은 파티션 내에서는 메시지 순서를 보장한다.
- **느슨한 결합**: 발행자와 소비자가 서로를 직접 알지 않고 토픽을 통해 통신한다.

즉 Kafka 도입은 "이벤트를 **어떻게 전달하느냐**"를 인메모리에서 메시지 브로커로 바꾸는 작업이며, 이는 이후 서비스 분리(MSA)와 대용량 트래픽 처리를 위한 전제 조건이 된다.

## 핵심 구성 요소

### Broker (브로커)

하나의 Kafka 서버 인스턴스를 의미한다. Producer로부터 메시지를 수신해 **offset** 기준으로 디스크에 저장하고, Consumer의 요청에 따라 저장된 메시지를 전달한다.

### Producer (프로듀서)

메시지를 브로커에 **발행(publish)** 하는 주체다. 기본적으로 Kafka가 어떤 Partition에 기록할지 자동으로 결정하지만, **메시지 key 기반 라우팅** 또는 **사용자 정의 Partitioner**로 특정 Partition에 보낼 수 있다. 같은 key는 항상 같은 파티션으로 가므로, 순서를 보장해야 하는 단위(예: 주문 ID)를 key로 지정하면 그 단위의 순차 처리가 보장된다.

### Consumer (컨슈머)

브로커에 저장된 메시지를 **소비(consume)** 하는 주체다. 하나 이상의 Topic을 구독하며, **Partition 단위로 offset을 관리**해 메시지를 순차적으로 읽는다.

- **Current Offset**: 현재 읽고 있는 위치
- **Committed Offset**: 실제로 처리 완료로 커밋한 위치

offset을 언제 커밋하느냐(처리 전 vs 처리 후)에 따라 **중복 소비** 또는 **유실**이 발생할 수 있어, 커밋 시점 관리가 중요하다.

### Topic (토픽)

메시지를 분류하는 **논리적 단위**다. 하나의 Topic은 여러 Partition으로 구성된다. Producer는 Topic 단위로 발행하고, Consumer는 Topic을 구독한다.

### Partition (파티션)

Topic을 구성하는 **물리적 단위**로, 병렬 처리와 순서 보장의 기준이다. 각 Partition 내부에서는 메시지 순서가 보장된다. 동시에 처리되면 안 되는 리소스를 Partition Key로 지정하면 **동시성 제어 + 순차 처리**를 함께 얻을 수 있다.

### Consumer Group (컨슈머 그룹)

하나의 Topic을 **여러 Consumer가 나눠 병렬 처리**하도록 묶는 단위다. 하나의 Partition은 그룹 내 **오직 하나의 Consumer에게만** 할당되므로, 같은 메시지를 중복 소비하지 않으면서 부하를 분산한다.

반대로 **서로 다른 그룹**은 같은 Topic을 각자 독립적으로 소비한다. 예를 들어 "주문 완료" 메시지를 랭크 서비스와 메시지 서비스가 각각 다른 Consumer Group으로 구독하면, 둘 다 독립적으로 그 이벤트를 받는다. 보통 **애플리케이션(서비스) 단위로 Consumer Group을 구성**한다.

### Rebalancing (리밸런싱)

Consumer Group 내에서 Partition 소유권이 재분배되는 과정이다. 새 Consumer 추가, 기존 Consumer 장애, Partition 추가 시 자동으로 일어난다. 확장성·가용성을 높이는 핵심 메커니즘이지만, 진행 중에는 일시적으로 소비가 멈추고 **중복 소비**가 발생할 수 있다.

### Replication (레플리케이션)

데이터 내구성을 위한 복제 기능이다. 각 Partition은 하나의 **Leader Replica**와 여러 **Follower Replica**로 구성된다.

- **Leader**: 쓰기/읽기를 담당하며 파티션당 하나만 존재
- **Follower**: Leader 데이터를 복제해 백업하고, 장애 시 동기화된 Follower가 Leader로 승격

Leader와 동기화된 복제본 집합을 **ISR(In-Sync Replica)** 이라 하며, ISR에 속하지 않은 Follower는 Leader로 승격될 수 없다.

### Cluster (클러스터)

여러 Broker를 하나의 논리적 단위로 묶어 **고가용성과 확장성**을 제공한다. Broker를 수평 확장하면 운영 중인 브로커에 영향을 주지 않고 처리·저장을 분산할 수 있다.

## 메시지 흐름과 파티션·컨슈머 비율

기본 흐름은 다음과 같다.

1. Producer가 메시지를 특정 Topic에 발행한다.
2. Broker가 지정된 Partition에 메시지를 저장한다.
3. Consumer가 Topic을 구독해 할당된 Partition에서 메시지를 소비한다.

병렬 처리 성능은 **Partition 수와 Consumer 수의 비율**에 크게 좌우된다. (Producer 수는 성능과 큰 관련이 없다.)

| 구성            | 동작                                | 활용                                 |
|---------------|-----------------------------------|------------------------------------|
| **파티션 > 컨슈머** | 한 컨슈머가 여러 파티션 담당, 순차 처리라 느려질 수 있음 | 처리를 의도적으로 지연(throttling)해 DB 부하 분산 |
| **파티션 = 컨슈머** | 컨슈머가 파티션 1:1 전담, 완전 병렬            | 처리량 극대화 (가장 이상적)                   |
| **파티션 < 컨슈머** | 남는 컨슈머는 유휴(idle) 대기               | 장애 시 리밸런싱으로 즉시 대체, 고가용성 여유         |

## 전달 보장과 주의사항

### 전달 시맨틱

- **at-most-once**: 최대 1회. 유실 가능, 중복 없음.
- **at-least-once**: 최소 1회. 유실 없음, **중복 가능**. (Kafka 기본)
- **exactly-once**: 정확히 1회. 이상적이지만 구현 비용이 크다.

Kafka는 기본적으로 at-least-once이므로, **중복은 반드시 고려**해야 한다.

### 메시지 유실 방지 — 트랜잭셔널 메시징

도메인 로직은 성공했는데 이벤트 발행이 실패하면, 그 이벤트를 기다리는 소비자가 후속 로직을 못 해 **전체 정합성이 깨진다**. 이를 막으려면 **도메인 로직과 이벤트 발행을 원자적으로** 묶어야 하며, 이를 트랜잭셔널 메시징이라 한다. 대표 방법:

- **Outbox 패턴**: 이벤트를 먼저 같은 DB 트랜잭션 안에서 Outbox 테이블에 저장하고, 별도 프로세스가 이를 읽어 Kafka로 발행한다. → 도메인 커밋과 이벤트 기록이 한 트랜잭션이라 유실이 없다.
- **CDC(Change Data Capture)**: DB 변경 로그를 감지해 Kafka 이벤트로 변환·전송한다.

### 메시지 중복 처리 — 멱등성

리밸런싱·재시도 등으로 같은 메시지가 **중복 소비**될 수 있으므로, 소비 로직은 같은 메시지를 여러 번 받아도 결과가 같도록 **멱등성(idempotency)** 을 가져야 한다. 처리한 메시지 ID를 기록해 재처리를 걸러내는 **Inbox 패턴**이 대표적이다.

### 메시지 실패 대응

소비 중 예외가 나면 무한 재시도로 컨슈머가 멈출 수 있다. **재시도 횟수 제한 + DLT(Dead Letter Topic)** 로 실패 메시지를 격리하고, 에러 로깅·모니터링으로 후처리한다.

## Outbox 패턴 구현

앞서 정리한 트랜잭셔널 메시징을 `common:outbox` 모듈로 구현하였다.  
핵심 목표는 **도메인 데이터 커밋과 이벤트 기록을 하나의 트랜잭션으로 묶는 것**이다.

### 아웃박스 테이블

```java
@Getter
@Entity
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Outbox implements Message {

    @Id
    @Column(name = "outbox_id")
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String eventId;

    @Enumerated(EnumType.STRING)
    @Column(length = 100)
    private EventType eventType;

    private Long partitionKey;

    @Lob
    @Column(columnDefinition = "TEXT")
    private String payload;

    private LocalDateTime createdAt;

    @Override
    public String getTopic() {
        return eventType.getTopic();
    }

    @Override
    public String getKey() {
        return String.valueOf(partitionKey);
    }
}
```

두 가지 설계 결정이 있다.

- **`Message` 인터페이스를 직접 구현하였다.** 엔티티가 토픽과 파티션 키를 스스로 제공하므로, 발행 시점에 별도의 변환 객체가 필요하지 않다.
- **발행 상태 컬럼을 두지 않았다.** `PENDING`, `PUBLISHED` 같은 상태를 관리하는 대신 **발행이 확인되면 행을 삭제**한다. 상태 컬럼 방식은 발행 성공 후 상태 갱신이 실패하면 다시 미발행으로 남는 문제가 있고, 삭제 방식은 그 중간 상태가 존재하지 않는다.

`partitionKey`는 주문·결제 이벤트 모두 `orderId`를 사용한다. 같은 주문의 이벤트가 항상 같은 파티션에 들어가므로 **주문 단위 순서가 보장**된다.

### 트랜잭션 경계

발행 요청은 스프링 애플리케이션 이벤트로 전달되며, 리스너가 두 단계로 나누어 처리한다.

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class OutboxEventListener {

    private final OutboxService outboxService;

    @TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)
    public void createOutbox(OutboxEvent event) {
        outboxService.createOutbox(event.getOutbox());
    }

    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void produceEvent(OutboxEvent event) {
        outboxService.produceEvent(event.getOutbox());
    }
}
```

- **`BEFORE_COMMIT`에서 아웃박스를 저장한다.** 비즈니스 트랜잭션과 같은 스레드·같은 트랜잭션에서 실행되므로, 아웃박스 저장이 실패하면 도메인 데이터도 함께 롤백된다. **원자성이 확보되는 지점**이다.
- **`AFTER_COMMIT`에서 Kafka로 전송한다.** `@Async`가 붙어 별도 스레드에서 실행되므로 응답 지연에 영향을 주지 않는다. 전송이 실패해도 도메인 데이터는 이미 확정되어 있고, 아웃박스 행이 남아 있으므로 유실되지 않는다.

이 구조에서 전체 흐름은 다음과 같다. 주문 생성을 예로 든다.

| 단계 | 동작                                    | 트랜잭션         |
|----|---------------------------------------|--------------|
| 1  | `OrderService.createOrder()` 도메인 저장   | 비즈니스 트랜잭션 내부 |
| 2  | `BEFORE_COMMIT` — `outbox` 테이블 INSERT | 비즈니스 트랜잭션 내부 |
| 3  | 커밋 (주문 + 아웃박스 동시 확정)                  | -            |
| 4  | `AFTER_COMMIT` — Kafka 전송             | 트랜잭션 외부, 비동기 |
| 5  | 자기 이벤트를 되읽어 아웃박스 행 삭제                 | 컨슈머의 별도 트랜잭션 |
| 6  | 삭제되지 않은 행을 스케줄러가 재발행                  | 스케줄러 트랜잭션    |

### 발행 확인과 행 삭제

발행 완료 판단을 **프로듀서 콜백이 아니라 컨슈머 수신 시점**에 하였다.

```java
@KafkaListener(topics = {
        Topic.COUPON_PUBLISH_REQUESTED, Topic.ORDER_COMPLETE_FAILED, Topic.ORDER_COMPLETED,
        Topic.ORDER_CREATED, Topic.PAYMENT_PAID, Topic.PAYMENT_FAILED, Topic.PAYMENT_CANCELED,
}, groupId = GroupId.OUTBOX + "-${spring.application.name}")
public void handle(String message, Acknowledgment ack) {
    Event<?> event = Event.of(message, Object.class);
    outboxService.clearOutbox(event.getEventId());
    ack.acknowledge();
}
```

자신이 발행한 이벤트를 다시 구독하여 `eventId`로 아웃박스 행을 삭제한다.  
프로듀서 콜백은 "브로커가 응답했다"까지만 보장하지만, 이 방식은 **"메시지가 실제로 다시 읽힐 수 있는 상태"** 를 확인한 뒤 삭제한다.

컨슈머 그룹 ID에 `${spring.application.name}`을 붙인 이유는, 각 서비스가 자기 아웃박스만 정리해야 하기 때문이다.  
그룹을 공유하면 파티션이 한 서비스에만 할당되어 다른 서비스의 아웃박스가 영구히 남는다.

`deleteByEventId`는 대상이 없으면 아무 일도 하지 않으므로, 메시지가 중복 수신되어도 안전하다.

### 재발행 스케줄러

4단계 전송이 실패했거나 5단계 되읽기가 이루어지지 않으면 행이 남는다. 이를 스케줄러가 되잡는다.

```java
@Scheduled(fixedDelay = 10, initialDelay = 5, timeUnit = TimeUnit.SECONDS)
public void publishPendingEvent() {
    try {
        outboxService.publishPendingEvent();
    } catch (Exception e) {
        log.error("Outbox 스케줄러 실행 중 오류 발생", e);
    }
}
```

```java
@Transactional
public void publishPendingEvent() {
    outboxRepository.findPendingEvent(
            LocalDateTime.now().minusSeconds(10),
            Pageable.ofSize(100)
    ).forEach(this::produceEvent);
}
```

미발행 판단 기준은 **생성 후 10초가 지났는데도 테이블에 남아 있는 행**이다. 상태 컬럼이 없으므로 행의 존재 자체가 미발행을 의미한다.  
`createdAt` 오름차순으로 100건씩 처리하여, 장애 복구 시 한 번에 과도한 부하가 걸리지 않도록 하였다.

예외를 `catch`로 삼키는 이유는 스케줄러 스레드가 죽지 않게 하기 위함이다.  
`fixedDelay` 방식은 예외가 전파되면 이후 실행이 중단되므로, 재발행 실패가 재발행 기능 자체를 멈추게 만든다.

### 남은 한계

- **`eventId`에 유니크 제약이 없다.** 스케줄러가 재발행한 이벤트와 원래 전송이 모두 도달하면 컨슈머가 같은 이벤트를 두 번 받는다. 중복은 컨슈머 측 멱등성으로 막는다.
- **재발행 시 in-flight 표시가 없다.** 스케줄러 실행 주기(10초)보다 재발행이 오래 걸리면 같은 행을 다시 집을 수 있다.
- **`createdAt`에 인덱스가 없다.** 아웃박스가 정상 동작하면 테이블이 거의 비어 있어 문제가 드러나지 않지만, 장애로 행이 누적되면 조회 비용이 증가한다.

## DLT(Dead Letter Topic) 구성

컨슈머에서 예외가 발생하면 `ack`가 수행되지 않아 **같은 메시지를 무한히 재소비**한다.  
이때 그 파티션의 후속 메시지는 전부 대기하므로, 하나의 실패 메시지가 파티션 전체를 멈춰 세운다.

재시도 횟수를 제한하고, 한계를 넘긴 메시지를 별도 토픽으로 격리하도록 구성하였다.

```java
@Bean
public DeadLetterPublishingRecoverer deadLetterPublishingRecoverer(KafkaTemplate<String, String> kafkaTemplate) {
    return new DeadLetterPublishingRecoverer(kafkaTemplate, (record, exception) -> {
        String deadLetterTopic = record.topic() + DLT_SUFFIX;

        log.error("카프카 메세지 처리 실패 - DLT 전송: topic={}, key={}, dlt={}",
                record.topic(), record.key(), deadLetterTopic, exception);

        return new TopicPartition(deadLetterTopic, ANY_PARTITION);
    });
}

@Bean
public DefaultErrorHandler kafkaErrorHandler(DeadLetterPublishingRecoverer deadLetterPublishingRecoverer) {
    DefaultErrorHandler errorHandler = new DefaultErrorHandler(
            deadLetterPublishingRecoverer,
            new FixedBackOff(RETRY_INTERVAL_MS, MAX_RETRY_ATTEMPTS)
    );

    errorHandler.setLogLevel(KafkaException.Level.ERROR);

    return errorHandler;
}
```

| 설정      | 값                   | 의미                                |
|---------|---------------------|-----------------------------------|
| 재시도 간격  | 1초 (`FixedBackOff`) | 일시적 장애의 회복 시간 확보                  |
| 재시도 횟수  | 3회                  | 최초 1회 포함 총 4회 시도                  |
| DLT 토픽  | `원본토픽 + ".DLT"`     | 예: `outside.order.created.v1.DLT` |
| DLT 파티션 | `-1`                | 자동 선택                             |

DLT 파티션을 `-1`로 지정한 이유는 **원본 토픽과 DLT의 파티션 수가 다를 수 있기 때문**이다.  
원본 파티션 번호를 그대로 사용하면, 원본이 3개 파티션이고 DLT가 1개일 때 존재하지 않는 파티션으로 전송하여 실패한다.

이 설정은 `common:message`의 자동 설정으로 등록되므로, 해당 모듈을 의존하는 모든 서비스(coupon, order, payment, product)에 별도 작업 없이 적용된다.  
`DefaultErrorHandler`가 `CommonErrorHandler` 타입의 단일 빈이므로 Spring Boot가 리스너 컨테이너에 자동으로 주입한다.

### 재시도가 무의미한 경우

현재 재시도 제외 예외를 지정하지 않았으므로, 프레임워크 기본 분류만 적용된다.  
그 결과 **재시도해도 절대 성공할 수 없는 예외까지 4회를 시도한다.**

예를 들어 "주문이 존재하지 않습니다"(`IllegalArgumentException`)는 데이터가 없어서 발생한 것이므로 1초 뒤에도 결과가 같다.  
이런 예외는 `addNotRetryableExceptions()`로 즉시 DLT로 보내는 것이 적절하다. 개선 대상으로 남겨 두었다.

### DLT 이후

DLT는 현재 **격리와 로깅 용도로만 사용**한다. DLT를 다시 소비하는 리스너나 재처리 배치는 없다.  
운영 환경이라면 DLT 적재를 알림으로 연결하고, 원인을 해소한 뒤 원본 토픽으로 되돌리는 재처리 경로가 필요하다.

## 적용 방향

현재 우리는 이벤트 발행을 `OrderEventPublisher` 같은 **인터페이스로 추상화**해 두고 `...SpringEventPublisher` 구현체가 `ApplicationEventPublisher`에 위임하고 있다. Kafka 전환은 이 구조 덕에 다음처럼 진행된다.

- 발행: 구현체를 **Spring → Kafka Producer**(토픽 발행)로 교체
- 소비: 리스너를 **`@KafkaListener` 컨슈머**로 전환
- 도메인 로직과 이벤트 정의는 그대로 유지

진행 순서(STEP08):

1. 외부 데이터 플랫폼 전송(Message)을 Kafka 메시지로 전환
2. 대용량 트래픽 영역(쿠폰 발급 등)을 Kafka로 전환, 토픽·컨슈머 그룹 정의
3. Outbox 패턴으로 발행 원자성 확보
4. 이후 서비스 분리(MSA) 시 Kafka가 서비스 간 통신 백본이 됨

> 도입 전 확인 사항: Spring Boot 4 호환 `spring-kafka` 버전, 메시지 역직렬화의 Jackson(Jackson3) 정합, `docker-compose`에 Kafka 브로커 추가.
