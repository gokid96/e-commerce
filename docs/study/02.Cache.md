# 캐시 기초 및 전략

## 캐시란

캐시는 **자주 조회되는 데이터나 연산 결과를 더 빠른 저장소에 임시로 보관하는 기법**이다.  
느린 저장소(RDB, 외부 API)에 반복 접근하는 대신, 메모리에 저장한 값을 반환하여 응답 시간과 원본 저장소의 부하를 줄인다.

## 왜 도입하는가

RDB의 처리 한계에 도달했을 때 선택지는 세 가지다.

- **스케일 업**: 인스턴스 사양을 높인다. 비용이 급격히 증가하고 상한이 존재한다.
- **스케일 아웃**: 읽기 복제본을 추가한다. 쓰기 부하는 분산되지 않고 복제 지연이 생긴다.
- **캐시**: 반복되는 읽기를 원본에 도달하기 전에 처리한다.

외부 API 응답은 직접 최적화할 수 없으므로, 이 경우 캐시가 사실상 유일한 수단이다.

다만 캐시는 만능이 아니다. **읽기가 쓰기보다 압도적으로 많고, 같은 데이터가 반복 조회되는 경우**에만 효과가 있다.  
매번 다른 데이터를 조회하는 패턴에서는 캐시 미스만 누적되어 오히려 지연이 늘어난다.

## 캐시의 근본 문제

캐시를 도입하면 **같은 데이터가 두 곳에 존재**하게 된다. 원본이 변경되었을 때 캐시가 갱신되지 않으면 불일치가 발생한다.

정합성 요구 수준은 데이터 성격에 따라 다르다.

| 데이터      | 정합성 요구 | 판단                       |
|----------|--------|--------------------------|
| 인기 상품 순위 | 낮음     | 몇 분 전 순위를 보여도 문제가 되지 않는다 |
| 상품 가격    | 중간     | 결제 시점에 원본으로 재검증하면 된다     |
| 재고 수량    | 높음     | 잘못된 값은 초과 판매로 직결된다       |
| 잔액       | 높음     | 캐시로 처리해서는 안 된다           |

따라서 캐시 도입의 첫 단계는 성능 개선 대상을 찾는 것이 아니라, **정합성을 양보할 수 있는 데이터를 찾는 것**이다.

## 캐시 전략

### 읽기 전략

#### Look Aside (Cache Aside)

캐시를 먼저 조회하고, 미스면 원본에서 읽어 캐시에 채운 뒤 반환한다.

```
조회 → 캐시 확인 → (미스) → DB 조회 → 캐시 저장 → 응답
```

캐시가 비어 있거나 장애가 발생해도 DB로 조회가 넘어가므로 **가용성이 높다**.  
반면 첫 요청은 항상 미스이므로 느리고, 캐시에 무엇이 들어갈지 사전에 통제할 수 없다.

데이터 양이 많고 조회 분포가 넓은 경우에 적합하다. 상품 상세 조회가 대표적이다.  
전체 상품을 미리 캐시에 적재하는 것은 비효율적이고, 실제로 조회된 것만 캐시에 남는 편이 낫다.

#### Read Through

캐시만 조회한다. 캐시에 없으면 원본을 조회하지 않는다.

캐시가 곧 데이터 소스이므로 **캐시가 비면 장애로 직결**된다.  
따라서 애플리케이션 시작 시점이나 배치로 캐시를 미리 채우는 **웜업이 전제**된다.

조회 대상이 소수로 한정되고 반복 조회가 많은 경우에 적합하다. 인기 상품 Top5 조회가 대표적이다.  
조회 키가 사실상 고정되어 있으므로 미리 적재할 수 있고, 매 요청 집계 연산을 반복하지 않아도 된다.

### 쓰기 전략

#### Write Around

쓰기는 원본에만 하고, 캐시는 미스가 발생할 때만 채운다.

구현이 가장 단순하지만 **원본 변경이 캐시에 즉시 반영되지 않는다.**  
TTL이 만료되거나 명시적으로 무효화할 때까지 캐시는 낡은 값을 반환한다.

#### Write Through

원본과 캐시에 동시에 쓴다.

캐시가 항상 최신이므로 **정합성이 보장**된다. 대신 쓰기 지연이 두 저장소의 합이 되고,  
조회되지 않을 데이터까지 캐시에 적재되어 메모리를 낭비할 수 있다.

#### Write Back (Write Behind)

캐시에만 쓰고, 일정 주기로 원본에 일괄 반영한다.

쓰기 성능이 가장 좋고 원본의 쓰기 부하를 크게 줄인다.  
그러나 **원본에 반영되기 전에 캐시가 소실되면 데이터가 유실**된다. 유실을 감수할 수 있는 데이터에만 사용해야 한다.

### 전략 비교

| 전략            | 장점                     | 단점                   | 적합한 경우        |
|---------------|------------------------|----------------------|---------------|
| Look Aside    | 캐시 장애에 유연, 필요한 데이터만 적재 | 첫 요청은 항상 미스          | 조회 분포가 넓은 데이터 |
| Read Through  | 반복 조회에 효율적, 집계 연산 회피   | 캐시 미스가 장애로 직결, 웜업 필요 | 조회 키가 한정된 데이터 |
| Write Around  | 구현이 단순, 불필요한 적재 방지     | 갱신 지연 발생             | 변경이 드문 데이터    |
| Write Through | 정합성 보장                 | 쓰기 지연 증가, 메모리 낭비     | 정합성이 중요한 데이터  |
| Write Back    | 쓰기 성능 우수, 원본 부하 감소     | 캐시 소실 시 데이터 유실       | 로그, 집계 카운터    |

## 캐시 스탬피드

특정 키의 캐시가 비어 있는 순간에 다수의 요청이 동시에 도착하면, **모든 요청이 캐시 미스로 판정되어 원본에 몰린다.**  
원본에는 읽기 부하가, 캐시에는 동일한 값을 쓰는 중복 쓰기 부하가 동시에 발생한다.

TTL 만료 시점이 겹치거나, 캐시 서버 재시작 직후에 발생하기 쉽다. 대응 방법은 다음과 같다.

- **캐시 웜업**: 트래픽이 도달하기 전에 미리 적재한다. 배치나 애플리케이션 초기화 시점에 수행한다.
- **TTL 분산(Jitter)**: 만료 시각에 임의 값을 더해 동시 만료를 방지한다.
- **재계산 잠금**: 미스가 발생하면 하나의 요청만 원본을 조회하고 나머지는 대기하게 한다. 분산 락으로 구현한다.
- **논리적 만료**: TTL보다 짧은 논리 만료 시각을 값에 담아, 만료가 임박하면 하나의 요청이 백그라운드로 갱신한다.

## 캐시 무효화

### TTL

일정 시간이 지나면 자동으로 삭제되도록 만료 시간을 지정한다.  
구현이 단순하고 캐시가 무한히 낡지 않도록 보장하지만, **TTL 기간 동안의 불일치는 허용**하게 된다.

TTL 설정은 정합성과 원본 부하 사이의 트레이드오프다. 짧게 잡으면 정합성이 좋아지고 미스가 늘어난다.

### 명시적 무효화

원본이 변경될 때 해당 캐시 키를 삭제하거나 갱신한다.

정합성이 좋지만 **변경 지점을 모두 찾아 처리해야 한다.** 누락되면 그 경로만 낡은 값을 반환하며, 원인 추적이 어렵다.  
또한 삭제와 갱신 중 무엇을 할지도 결정해야 한다. 삭제는 다음 조회가 느려지고, 갱신은 조회되지 않을 값을 미리 계산한다.

실무에서는 **명시적 무효화 + 짧지 않은 TTL**을 함께 쓴다. 무효화 누락이 있어도 TTL이 결국 정리하는 안전망이 된다.

## 만료 정책

캐시 메모리가 가득 찼을 때 무엇을 버릴지 결정하는 정책이다.

| 정책   | 기준              | 특징                           |
|------|-----------------|------------------------------|
| LRU  | 가장 오래 사용되지 않은 것 | 일반적인 조회 패턴에 무난하다             |
| LFU  | 가장 적게 사용된 것     | 인기 데이터를 오래 유지하지만 과거 인기에 편향된다 |
| FIFO | 가장 먼저 들어온 것     | 구현이 단순하나 조회 빈도를 반영하지 않는다     |
| TTL  | 만료 시각 도달        | 용량과 무관하게 시간 기준으로 제거한다        |

## 캐시 종류

### 로컬 캐시

애플리케이션 인스턴스의 힙 메모리에 저장한다.

- 네트워크를 경유하지 않아 가장 빠르다
- 인스턴스마다 독립된 캐시를 가지므로 **인스턴스 간 값이 불일치**할 수 있다
- 인스턴스가 종료되면 사라지고, 스케일 아웃하면 캐시 적중률이 인스턴스 수에 반비례해 떨어진다

### 글로벌 캐시

Redis 같은 외부 저장소를 여러 인스턴스가 공유한다.

- 인스턴스 수와 무관하게 일관된 값을 제공한다
- 네트워크 왕복이 있어 로컬 캐시보다 느리다
- 캐시 서버가 **단일 장애점**이 될 수 있어, 장애 시 원본으로 우회하는 경로가 필요하다

MSA 환경에서는 서비스가 독립적으로 확장되므로 글로벌 캐시가 기본 선택이다.  
로컬 캐시는 변경이 거의 없고 인스턴스 간 불일치가 문제되지 않는 데이터(설정값, 코드 테이블)에 한정해 쓰는 편이 안전하다.

## 적용 방향

본 프로젝트에서는 다음과 같이 적용하였다.

- **인기 상품 조회**: Read Through + 배치 웜업. 조회 키가 고정되어 있고 집계 연산이 무거워 선택하였다.
- **선착순 쿠폰 발급**: Redis를 캐시가 아닌 **선차단 수단**으로 사용. 발급 가능 여부만 Redis로 판정하고 실제 발급은 비동기로 처리한다.
